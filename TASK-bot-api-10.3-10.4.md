# Задание агенту: полное освоение Bot API 10.3 / 10.4 через скилл, код и практические сценарии

## Цель и рабочая область

Доработай существующий скилл `telegram-bot-ui` в `C:\Projects\telegram-bot-ui`, чтобы ИИ-агенты умели практически использовать ВЕСЬ набор возможностей, который дают обновления Telegram Bot API 10.3 и 10.4, включая сложные сочетания новых функций. Скилл должен научить агента переходить от пользовательской идеи к конкретной реализации: выбирать API, собирать корректный payload, обрабатывать события, поддерживать состояние и проверять пользовательский результат.

Нужен законченный апдейт самого скилла: инструкции, справочники, библиотека практических рецептов, исполняемые примеры, валидаторы и поведенческие проверки. Упоминание метода или ссылка на документацию не считаются обучением применению.

Интерфейс бота остаётся центральной областью, но прежние исключения `telegram-bot-ui` не должны обрезать покрытие обновлений. Расширь область скилла на необходимые новые API, события и интеграции из 10.3/10.4. Редкие или смежные возможности вынеси в отдельные модули по запросу: они тоже должны быть практически освоены. Включи управление состоянием, отмену, доставку обновлений, совместимость, Widgets и связанные wallet/business/community/managed-bot сценарии в пределах функций этих релизов. Не требуется писать общий учебник backend или блокчейна; требуется научить использовать конкретные возможности Telegram, включая их необходимую серверную часть. Обнови противоречащие этому ограничения и правила активации старого скилла.

**Приоритет пользователя:** максимально раскрыть возможности обновлений и снабдить агентов примерами. Не сокращай охват ради краткости или привычного старого стека. ## 1. Исходное состояние и подтверждённые проблемы

Предварительное исследование выполнено 12 ноября 2026 года. На эту дату официально опубликованы **10.3 от 24 августа** и **10.4 от 9 ноября 2026 года**. При начале работы перепроверь актуальность: не называй версию последней без даты проверки. Источник: [официальный changelog](https://core.telegram.org/bots/api-changelog).

Текущая база проверена преимущественно по 10.2. Изучи `SKILL.md`, `README.md`, `agents/openai.yaml`, `references/`, `scripts/` и `evals/`. Уже обнаружены следующие точки для исправления:

- `references/official-sources.md` и `references/ui-changelog.md` заканчиваются на 10.2; обновления 10.3/10.4 не встроены в рабочие решения.
- В `SKILL.md` есть универсальное утверждение об отсутствии CSS/layout у интерфейса бота. Его область действия нужно уточнить с учётом Widgets.
- `scripts/validate_keyboard.py` не распознаёт `disabled`. Локально воспроизведено отклонение `{"inline_keyboard":[[{"text":"Unavailable","disabled":{}}]]}` с сообщениями `unknown field 'disabled'` и `found 0 []`.
- В `references/streaming-and-editing.md` псевдокод после `Cancelled: break` безусловно отправляет финальный результат. Требуется явная политика отмены и защита от гонок.
- Там же смешиваются идентификаторы обычных forum topics и channel direct-message topics. Проверь контексты и поля адресации отдельно.
- `references/format-selection.md` навязывает таблицу практически любым структурированным данным. Нужны критерии удобства чтения, а не обязательное усложнение каждого сообщения.
- Часть rich-лимитов помечена как вторичная и неподтверждённая. Перепроверь статус каждого по текущей спецификации.
- Общие советы о fallback не фиксируют важнейший инвариант: персональный ответ нельзя превращать в публичный при ошибке.
- Проверки активации есть, но они не доказывают правильность выбора API и поведения при отказах.

На исходном состоянии `validate_skill.py` и `validate_references.py` проходят. Это проверка структуры пакета, а не его актуальности. Сохрани исходный результат и добавь проверки, которые выявляют реальные дефекты.

## 2. Исследование и доказательность

Используй официальную [Bot API reference](https://core.telegram.org/bots/api), [changelog](https://core.telegram.org/bots/api-changelog), [Widgets guide](https://core.telegram.org/bots/widgets), [Bot Features](https://core.telegram.org/bots/features) и при необходимости [Mini Apps](https://core.telegram.org/bots/webapps). Для SDK используй документацию, release notes и исходники именно проверяемой версии.

Сделай полный реестр **каждого пункта релизов 10.3/10.4**, включая новые методы, типы, поля, updates, изменения семантики и переименования. Для каждой строки укажи: версия → возможность → практическая польза → условия доступности → раздел скилла → пример → проверка → статус готовности. Категории «основной модуль» и «специализированный модуль» определяют размещение, но не освобождают от реализации. Не помечай новое API «вне области» только потому, что старый скилл его исключал.

Каждой самостоятельной возможности сопоставь конкретный пример. Связанные типы допустимо покрывать одним сценарием с явной привязкой к строкам реестра. Для нового поля покажи изменение поведения; для входящего события — fixture и обработчик; для переименования — миграцию до/после; для новой операции — запрос, результат и обработку ошибки. Тестовые возможности включи с отдельной маркировкой и способом воспроизведения, а не удаляй из покрытия.

Для существенных правил фиксируй ссылку на конкретный раздел, дату проверки и статус: требование API / официальная рекомендация / эвристика дизайна / результат локального теста / неподтверждённое предположение. При противоречии между официальными страницами явно опиши его и выбери обоснованное поведение; не скрывай неопределённость.

Разделяй пять вещей: наличие возможности в спецификации, доступность в production, поддержку сервера Bot API, поддержку установленного SDK и отображение клиентом. Не предполагай существование универсального API для определения версии клиента или всех возможностей бота.

Исторические схемы сохраняй только с явной маркировкой версии. Если вышла более новая версия, отметь её и влияние на решения, сохранив полное покрытие 10.3/10.4. Недоступность источника не компенсируй выдуманными полями.

## 3. Обязательные направления обновления

### 3.1. Кнопки и запрос ответа

Покрой изменения 10.3: `DisabledButton`, `InlineKeyboardButton.disabled`, `force_reply` в обеих клавиатурах; rich-кнопки `RichMessageButton`, `RichTextButton`, `RichBlockButtons` / `InputRichBlockButtons`. Источник: [релиз 10.3](https://core.telegram.org/bots/api-changelog#august-24-2026).

Разведи модели inline-, reply- и rich-кнопок; не копируй допустимые поля одной модели в другую. `disabled` — объект и отдельный вариант типа кнопки; нельзя просто добавить его к существующему `callback_data`. Для inline-клавиатуры значение `force_reply` нельзя менять при её редактировании. Источники: [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton), [InlineKeyboardMarkup](https://core.telegram.org/bots/api#inlinekeyboardmarkup).

Научи выбирать между отключением кнопки, её удалением, заменой подписи и сохранением действия с объяснением. Опиши поведение старых сообщений и восстановление управления после ошибки. Отключённая кнопка не заменяет серверную проверку состояния и прав. Отдельно объясни отличие поля `force_reply` от объекта `ForceReply` и критерии применения в формах.

### 3.2. Управляемая генерация

Добавь `can_stop`, `keep_on_stop`, `Update.stopped_message_generation` / `MessageGenerationStopped`. `keep_on_stop` не сохраняет ответ навсегда: для постоянного результата нужна отдельная отправка. Источники: [sendMessageDraft](https://core.telegram.org/bots/api#sendmessagedraft), [sendRichMessageDraft](https://core.telegram.org/bots/api#sendrichmessagedraft).

Опиши конечный автомат операции: запуск, генерация, запрос остановки, остановлено, успешно завершено, ошибка, истечение времени. Сопоставляй событие остановки с конкретной операцией и её контекстом. Покажи отмену upstream-генерации, отбрасывание поздних chunks, очистку очереди обновлений и гонку «Stop одновременно с завершением».

Раздели продуктовые варианты: отбросить частичный результат; сохранить его с понятной пометкой; предложить продолжить или повторить. Отмена не должна безусловно попадать в ветку успеха или ошибки. Формулируй «одна логическая финализация» как инвариант приложения, а не обещание exactly-once доставки по сети.

Учитывай `allowed_updates`, разбор нового Update SDK и совместимость входящих событий, а не только отправку новых методов. Пересмотри throttling: объединение событий не должно позволять каждой законченной фразе обходить минимальный интервал. После остановки таймеры и отложенные retry не должны оживлять поток. Прогресс отражает реальные этапы; thinking-блоки не должны раскрывать внутренние рассуждения модели или служебные данные.

### 3.3. Персональные и ephemeral-сценарии

Покрой переход 10.2 → 10.3 к `ephemeral_message_parameters`, `replace_callback_query_message`, rich-контент и редактирование ephemeral. Для 10.4 исследуй callback-ответ без `receiver_user_id` и условную необязательность `chat_id`, включая исключения по контекстам. Источники: [10.3](https://core.telegram.org/bots/api-changelog#august-24-2026), [10.4](https://core.telegram.org/bots/api-changelog#november-9-2026).

Ephemeral callback-ответ не отменяет `answerCallbackQuery`; доставка ephemeral не гарантирована. Отдельно проверь ограничения замены исходного сообщения. Источник: [EphemeralMessageParameters](https://core.telegram.org/bots/api#ephemeralmessageparameters).

Составь таблицу выбора: общий результат для чата, персональный ответ, персональное представление поверх общей карточки, постоянная запись результата. Покажи идентификацию пользователя, авторизацию доступа к данным, срок жизни состояния, обработку устаревших действий и повторных нажатий. Один участник не должен видеть состояние или результат другого.

Критический инвариант fallback: сохранить аудиторию, права, контекст и смысл. При невозможности персональной доставки не отправлять её содержимое в общий чат. Не обещать автоматическую доставку в личку, если доступ к ней не подтверждён. Различай временный draft и ephemeral message: сходство терминов не означает общий жизненный цикл.

### 3.4. Rich Messages и выбор формата

Покрой 10.3: `is_compact` таблиц, expandable quotation, document blocks и `tg://document?id=`. Покрой 10.4: rich-цитаты (`rich_texts`, `quote_rich_texts`), `RichTextTonAddress`, изменения entities, приватные topic-ссылки. Остальные изменения релизов также обеспечь практическими примерами в основном или специализированных модулях. Источник: [changelog](https://core.telegram.org/bots/api-changelog).

Перепроверь входные/выходные модели, вложенность, ссылки на media, доступность кнопок и форматирование цитат. Ограничения rich-сообщений теперь явно перечислены в [Rich Message Limits](https://core.telegram.org/bots/api#rich-message-limits); согласуй все локальные таблицы и пометки источников. В rich draft не поддерживаются прямая загрузка новых файлов и явная загрузка по URL. Источник: [sendRichMessageDraft](https://core.telegram.org/bots/api#sendrichmessagedraft).

Замени автоматическое «самый богатый формат» на осознанный выбор: задача пользователя, объём, сравнение по колонкам, мобильная читаемость, действия, доступность, поддержка и стоимость сопровождения. Сохрани сильную поддержку настоящих таблиц, но разреши короткий список фактов там, где он удобнее.

Нужна таблица решений между обычным сообщением, rich-документом, клавиатурой, embedded rich-кнопками, ephemeral-представлением, Widget и Mini App. Не смешивай обычный HTML parse mode, Rich HTML и HTML виджета. Для каждого важного сценария объясни причину выбора и условия перехода к альтернативе.

### 3.5. Widgets как новая поверхность UI

Создай самостоятельный, доступный по маршрутизации раздел о Widgets. В production сейчас доступны личные чаты с ботом; группы, inline и пересылки описаны для тестового сервера. Это нельзя выдавать за готовый production-сценарий. Источник: [Widgets guide](https://core.telegram.org/bots/widgets).

Изучи жизненный цикл отправки, изменения состояния и ответов на запросы: `sendWidget`, `sendSharedWidget`, `answerWidgetQuery`, `editMessageWidgetData`, `editSharedWidgetData`, новые updates. Источник: [релиз 10.4](https://core.telegram.org/bots/api-changelog#november-9-2026).

Обязательные правила: виджет самодостаточен и не имеет сетевого доступа; HTML после отправки неизменяем; `chat_data` и `public_data` имеют разные аудитории. Ответ на query не обновляет состояние. Caption нужен для поиска, уведомлений, доступности и клиентов без поддержки. Код и публичное состояние нельзя использовать для секретов. Источник: [Widgets guide](https://core.telegram.org/bots/widgets).

Документируй ограничения runtime, размеров и сжатия, данных, жестов, ввода, темы, RTL, safe areas и accessibility. Проверку размера реализуй по официальному алгоритму, не по приблизительной длине строки. Не проектируй обычную веб-страницу с произвольными browser API внутри сообщения.

Для query-потока покажи авторитетное серверное состояние, проверку пользователя и действия, повторные/устаревшие запросы, порядок answer и state update, ревизии состояния, timeout и отображение ошибок. Отдели данные, доступные всем читателям, от ответа конкретному действию. Для TON/wallet-событий создай отдельные примеры доступных типов запросов, ответов и проверки результата; уведомление не считай самостоятельным доказательством оплаченного заказа. Документируй границу между Telegram API, проверкой подписи и подтверждением транзакции, без вымышленных гарантий.

В качестве примера подойдёт компактная карточка заказа или выбор варианта с обновлением состояния. Дай полноценную текстовую/кнопочную альтернативу. Объясни, когда виджет оправдан, когда достаточно обычной клавиатуры и когда нужна Mini App. Не вводи Widgets как обязательный стандарт для каждого бота.

## 4. Инженерные правила, которые должны менять решения агента

- **SDK:** проверять request serialization, response parsing, update routing, модели и transport. Raw HTTP решает только часть проблемы; он не добавляет обработчики новых событий автоматически. Документированный адаптер должен быть изолирован и иметь условие удаления.
- **Контекст:** различать private/group/supergroup/channel/inline/business, обычные topics и channel direct-message topics. Набор полей определять по конкретному методу, не копировать универсальный payload.
- **Состояние:** проверять актуальность callback и права на сервере; обрабатывать повторы и гонки. При редизайне сохранять контракты callback/deep links либо явно проектировать совместимую миграцию.
- **Ошибки:** отделять validation, unsupported capability, permissions, rate limiting и неизвестный результат отправки после timeout. Не считать timeout доказательством недоставки; ограниченный retry тоже может создать дубликат.
- **Fallback:** сохранять аудиторию, доступные действия и значение результата. Не маскировать дефект payload бесконечным перебором форматов. Клиент может не отображать возможность даже при успешном ответе сервера.
- **Форматирование:** разделять экранирование по форматам, UTF-8 bytes и UTF-16 offsets; проверять Unicode, переносы, media references, разделение длинного контента и сохранение контекста.
- **UX:** внятные подписи, один понятный следующий шаг, возврат/отмена, сохранение введённого, empty/loading/error/stale/no-permission состояния, локализация и RTL. Количество акцентных кнопок и длина строки — эвристики, не ограничения Telegram.
- **Наблюдаемость:** фиксировать переходы состояния, выбор fallback и класс ошибки без токенов и лишних персональных данных. Технические детали не выводить пользователю без необходимости.

## 5. Устройство обновлённого скилла

Оставь `SKILL.md` компактным входом: назначение, границы, выбор режима, ключевые инварианты и маршруты к нужным справкам. Для маленькой правки подписи не требуй полного аудита всего бота; для миграции и сложного сценария используй расширенную проверку.

Новые тематические references добавляй только при самостоятельной пользе. Устрани дублирование между `dynamic-feedback-and-streaming.md` и `streaming-and-editing.md`, согласуй матрицы форматов, ограничений, версий и fallback. Не копируй официальную документацию целиком.

Согласуй description, UI metadata, README и activation evals с реальным охватом. Не меняй имя скилла без необходимости и сохрани автоматическую активацию. Не навязывай повторное разрешение на локальное обновление справок, уже входящее в порученную доработку.

Создай библиотеку рецептов и исполняемых примеров по требованиям ниже. Псевдокод допустим для объяснения архитектуры, но не заменяет рабочий пример ключевого механизма. Исполняемые примеры не должны ссылаться на вымышленные классы SDK; их версии и проверенные возможности укажи.

### 5.1. Формат обучающего рецепта

Каждый рецепт должен позволять агенту адаптировать его к чужому проекту без самостоятельного восстановления пропущенной логики. Включай:

1. Реалистичный запрос пользователя и ожидаемый видимый результат.
2. Почему новая возможность полезна именно здесь; что она позволяет сделать по сравнению с прежним подходом.
3. Минимальную версию, production/test-статус, чат-контекст, права и настройки.
4. Полный минимальный JSON payload с типами и осмысленными демонстрационными данными. Для событий — входящий fixture.
5. Рабочий код отправки/обработчика, используемые helpers и необходимые настройки получения updates. Не прячь основную логику за `handle_everything()` или `TODO`.
6. Последовательность запросов и событий, состояние до/после, связь идентификаторов.
7. Пример результата или его структуры; для визуального механизма — ожидаемый экран/взаимодействие. Макет явно отличай от настоящего клиентского скриншота.
8. Типичную ошибку использования и её исправление, существенные ограничения и работоспособную альтернативу.
9. Команду запуска, fixture/test и критерии проверки результата; честно указанный уровень фактической проверки.
10. Какие части копировать, какие адаптировать и куда встроить в существующем проекте. Дай перекрёстные ссылки на совместимые рецепты.

Сделай общий SDK-независимый слой payload-примеров и небольшие исполняемые harness/adapters на Python и TypeScript. Основные сквозные сценарии покажи на обоих языках; для редких API достаточно одного исполняемого варианта и общего payload, пригодного для второго адаптера. Выбери и проверь актуальные SDK; при пробелах покажи полноценный transport adapter. Зафиксируй зависимости и инструкции запуска. Offline-режим с fixtures должен работать без токена; live-режим включается явно для тестового бота.

### 5.2. Обязательные сквозные примеры

Подготовь как минимум следующие связные реализации, дополненные мини-рецептами для остальных строк реестра:

| Пример | Чему должен научиться агент |
|---|---|
| AI-помощник с богатым ответом | Rich streaming, реальные этапы, Stop, политика частичного результата, финальная публикация, защита от гонок |
| Интерактивный документ | Компактная таблица, раскрываемая цитата, вложенный документ, кнопки внутри rich-контента, цитирование выбранного фрагмента |
| Многошаговая форма | Клавиатура вместе с запросом ответа, disabled-состояния, валидация, возврат, повторная отправка без дублирования |
| Общая карточка и персональная панель | Ephemeral callback response/overlay, независимые действия двух пользователей, редактирование и защита аудитории |
| Интерактивный Widget в личном чате | Полный HTML/CSS/JS, отправка, query handler, изменение состояния, caption, тема, мобильная компоновка, ошибки |
| Shared Widget | Создание, повторное использование, общее состояние, обновления и ревизии; отдельные явно тестовые варианты групп/inline/пересылок |
| Wallet-взаимодействие | Доступные варианты запросов, подпись/transaction-событие, проверка и понятное пользователю состояние результата |
| Бот с несколькими темами диалога | Контекст операции и сообщения, переход по topic-ссылке, изоляция параллельных ответов |

В каждом примере реально соедини нужные возможности в один поток. Набор несвязанных JSON-фрагментов не заменяет сквозной пример. Предусмотри index/manifest для поиска рецепта по задаче, API-символу, версии и контексту; файлы примеров должны быть достижимы из скилла.

Добавь правило инициативного применения: при создании или серьёзной доработке бота агент проверяет, какие возможности обновлений улучшат заданные сценарии, и реализует подходящие в разрешённом объёме. Он не должен ждать, пока пользователь сам назовёт метод. Для маленькой локальной правки не инициируй несвязанный редизайн.

## 6. Валидаторы и проверяемость

Обнови `validate_keyboard.py` и добавь необходимые regression fixtures. Проверяй модели отдельно; различай отсутствие поля, `null`, `false` и пустой объект. Ошибки структуры отделяй от UX-предупреждений. Не изображай полную schema validation там, где проверяется только часть полей.

Нужны минимум следующие содержательные проверки:

1. Корректный disabled-вариант проходит; `disabled` вместе с действием и неверный тип отклоняются.
2. Inline/reply/rich-кнопки не принимают поля друг друга по ошибке; сохраняются проверки размера callback в байтах.
3. Force-reply сценарий учитывает ограничения редактирования.
4. Успех, остановка, ошибка и timeout генерации имеют разные завершения; поздние chunks и повторный Stop не создают результат повторно.
5. Персональный fallback не становится публичным; два участника не получают данные друг друга.
6. Старый SDK не теряет новые поля/updates незаметно: проверяется реальный сериализованный payload и входящий fixture.
7. Примеры Widgets учитывают production/test, размер, аудитории состояния и отсутствие runtime-возможностей, на которые опирается обычная веб-страница.
8. Обработка 429 не создаёт tight loop; неопределённый результат send не объявляется безопасным для безусловного повторения.
9. Unicode, экранирование и split сохраняют содержимое, ссылки, клавиатуру и адресацию.

Используй существующий тестовый механизм либо лёгкие offline-тесты на стандартной библиотеке. Не добавляй тяжёлый framework ради проверки Markdown. Фикстуры должны проверять поведение и инварианты, не совпадение формулировок и заголовков.

Добавь поведенческие evals: реалистичный запрос, минимальный контекст, наблюдаемые критерии успеха и критические ошибки. Охвати простое меню без rich, таблицу сравнения, форму, остановку AI-ответа, приватный ответ в группе, Widget в production, устаревший SDK, устаревшую кнопку и сетевую неопределённость. Добавь задания на комбинирование возможностей и специализированные модули. Обнови отрицательные проверки активации: несвязанный DevOps остаётся вне области, но серверная обработка новых Telegram-событий должна активировать нужный модуль.

Проверь перенос знаний: агент получает новую предметную задачу без названий нужных методов и без готового ответа, находит рецепты и создаёт работающую адаптацию. В другом задании измени язык, SDK, тип чата или доступность функции. Успех — корректная реализация и проверки, а не перечисление возможностей. При отсутствии среды для настоящего агентного прогона подготовь воспроизводимый eval-набор и явно отметь его как не запущенный; ручное прочтение не выдавай за агентный тест.

Разделяй уровни доказательства: статическая проверка, unit/contract fixture, реальный Bot API, реальные клиенты. Нельзя объявлять Android/iOS/Desktop/Web проверенными на основании JSON или браузерного preview. Если нет разрешённого тестового бота/клиента, заверши offline-часть и явно перечисли оставшиеся live-проверки. Не запрашивай production-токен ради тестов скилла.
